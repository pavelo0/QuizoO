При проектировании web-приложения QuizoO в первую очередь был определён архитектурный подход, позволяющий разделить пользовательский интерфейс, бизнес-логику и хранение данных. QuizoO представляет собой платформу для самостоятельного закрепления знаний: пользователь создаёт учебные модули, наполняет их карточками или вопросами квиза, проходит обучение и получает статистику по результатам.

В качестве базовой архитектуры выбрана трёхуровневая клиент-серверная модель. Первый уровень — браузерное SPA-приложение, отвечающее за интерфейс пользователя. Второй уровень — сервер REST API, реализующий аутентификацию, управление учебными модулями, проверку ответов и административные функции. Третий уровень — реляционная база данных PostgreSQL, где хранятся пользователи, модули, вопросы, варианты ответов и результаты учебных сессий.

Клиентская и серверная части взаимодействуют по протоколу HTTPS. Внешней точкой входа выступает Nginx: он принимает запросы браузера, отдаёт собранные статические файлы frontend-приложения и проксирует обращения `/api/*` на backend-сервис по внутреннему HTTP-соединению. Такая схема упрощает развёртывание, скрывает внутренние сервисы от прямого доступа и позволяет централизованно настраивать TLS.

Выбор технологий осуществлялся исходя из зрелости экосистемы, удобства разработки на TypeScript и соответствия задачам образовательного web-приложения. Итоговый технологический стек представлен в таблице 2.1.

Для доставки кодов верификации и сброса пароля в проектной записке целесообразно указать Nodemailer как простую и распространённую библиотеку отправки email через SMTP. Для карточек задаются пары «вопрос – ответ», а для квиза создаются вопросы одного из трёх типов: выбор ответа, текстовый ответ или сопоставление. После наполнения модуля пользователь запускает режим обучения, проходит материал и получает сохранённый результат.

Структура базы данных спроектирована на основе реляционной модели и описана в Prisma Schema. Центральными сущностями предметной области являются пользователь, учебный модуль, карточка, вопрос и учебная сессия. Связи между таблицами построены так, чтобы каждый пользователь работал со своими модулями, а удаление модуля автоматически удаляло вложенный учебный контент и связанные результаты.

Таблица users хранит данные учётных записей. Помимо email и хэша пароля, в ней находятся роль пользователя, флаг блокировки, OAuth-идентификаторы, состояние подтверждения email, коды верификации и сброса пароля, MIME-тип аватара и временные метки создания и обновления. Роль пользователя задаётся перечислением UserRole со значениями USER и ADMIN.

Таблица modules хранит учебные модули. Каждый модуль принадлежит одному пользователю и имеет тип ModuleType: FLASHCARD или QUIZ. Для модуля сохраняются название, описание, дата создания и дата обновления. В зависимости от типа модуль содержит либо карточки, либо вопросы квиза.

Таблица cards используется для модулей типа FLASHCARD. В ней хранится текст вопроса, текст ответа и поле orderIndex, определяющее порядок карточек в редакторе и режиме обучения. Каждая карточка связана с одним модулем, а при удалении модуля удаляется каскадно.

Таблица questions используется для модулей типа QUIZ. Вопрос имеет текст, тип, флаг allowMultipleAnswers для поддержки множественного выбора, MIME-тип изображения вопроса и порядковый индекс. Для вопросов типа CHOICE используются связанные записи question_options, для вопросов типа MATCHING — связанные записи matching_pairs. Для текстового вопроса правильный ответ может быть представлен через варианты ответа либо проверяться логикой сервиса в зависимости от конкретной реализации сценария.

Таблица question_options хранит варианты ответа для вопросов с выбором. Каждый вариант содержит текст и флаг isCorrect. За счёт нескольких записей с isCorrect=true поддерживается режим множественного выбора.

Таблица matching_pairs хранит пары сопоставления. Каждая запись содержит левый и правый элемент, относящиеся к одному вопросу. При прохождении квиза пользователь должен сопоставить элементы, а backend проверяет соответствие сохранённым парам.

Таблица flashcard_sessions фиксирует результат прохождения карточек. Для каждой сессии сохраняются пользователь, модуль, общее количество карточек, количество известных и неизвестных карточек, а также дата завершения.

Таблица quiz_sessions фиксирует результат прохождения квиза. Для сессии сохраняются пользователь, модуль, общее количество вопросов, количество правильных ответов, процент результата и дата завершения. Детализация ответов хранится в таблице quiz_answers.

Таблица quiz_answers связывает сессию квиза и конкретный вопрос. В поле userAnswer сохраняется ответ пользователя в JSON-совместимом строковом представлении, а поле isCorrect фиксирует результат проверки. Для пары sessionId и questionId задано уникальное ограничение, чтобы в одной сессии на один вопрос приходился только один итоговый ответ.

Это означает, что при удалении пользователя удаляются его модули и сессии, а при удалении модуля удаляются вложенные карточки, вопросы и результаты прохождения. Такой подход соответствует предметной области: карточка или вопрос не имеют смысла вне своего модуля.

2.4 Проектирование серверной логики и API

Серверная часть построена на NestJS и разделена на функциональные модули. Глобальный префикс API — `/api`. Входящие данные проходят через ValidationPipe с включённым whitelist и transform, что позволяет отбрасывать лишние поля и приводить DTO к ожидаемому виду.

Модуль Auth отвечает за регистрацию, подтверждение email, вход, выход, сброс пароля, смену email и пароля, а также Google OAuth. После успешной аутентификации backend устанавливает JWT в httpOnly cookie. Доступ к защищённым маршрутам контролируется глобальным JwtAuthGuard; публичные маршруты помечаются отдельным декоратором Public.

Для подтверждения email и сброса пароля используются шестизначные коды с ограниченным сроком действия. В проектной версии для отправки таких кодов выбран Nodemailer: он прост в подключении, работает через SMTP и не требует привязки к конкретному внешнему провайдеру. Это удобно для курсового проекта, потому что в разработке можно использовать тестовый SMTP или локальный почтовый сервис, а в production заменить настройки на реальный почтовый ящик. В лабораторном режиме коды допускается выводить в лог сервера или возвращать в API-ответ при включённой переменной AUTH_RETURN_VERIFICATION_CODE.

Модуль Users отвечает за профиль пользователя и административные функции. Пользователь может получить данные текущей учётной записи, изменить username, сменить email и пароль, загрузить или удалить аватар. Администратор может получить сводную статистику, список пользователей, список модулей и заблокировать обычного пользователя.

Модуль Modules реализует основную бизнес-логику приложения. Он предоставляет API для списка модулей, создания, обновления и удаления модуля, управления карточками, управления вопросами квиза, загрузки изображений к вопросам, прохождения карточек и квизов, получения результата квиз-сессии, дашборд-сводки и недавней активности. Изображения вопросов и аватары сохраняются в файловом хранилище контейнера backend, а метаданные MIME-типа фиксируются в базе данных.

2.5 Проектирование клиентского приложения

Клиентская часть реализована как SPA на React и Vite. Маршрутизация построена с использованием React Router. Приложение имеет отдельные layout-компоненты для публичной страницы, страниц авторизации и внутреннего пользовательского раздела.

Публичная часть содержит лендинг и страницы авторизации. Для гостя доступны регистрация, вход, сброс пароля и обработка OAuth-callback. После входа пользователь попадает в защищённый раздел `/app`, доступ к которому контролируется компонентом RequireAuth.

Внутренний раздел включает дашборд, создание модуля, редактор карточек, редактор квиза, режим прохождения карточек, режим прохождения квиза, страницу статистики, профиль и onboarding. Для администратора предусмотрены защищённые маршруты административной панели: общий дашборд, пользователи, модули и аналитика. Доступ к ним контролируется компонентом RequireAdmin.

Обмен с backend выполняется через общий Axios-клиент. Базовый URL API задаётся переменной VITE_API_URL или по умолчанию равен `/api`, что позволяет одинаково работать через локальный dev-сервер и через Nginx в Docker-окружении. Запросы отправляются с `withCredentials: true`, так как JWT хранится в cookie.

2.6 Проектирование архитектуры развёртывания

Архитектура развёртывания приложения описывается Docker Compose окружением. В него входят четыре сервиса: postgres, backend, frontend-builder и nginx.

Сервис postgres запускает PostgreSQL 18 и хранит данные в volume postgres18_data. Сервис backend собирается из каталога `backend`, работает на Node.js 20 Alpine, при старте выполняет `prisma migrate deploy`, запускает NestJS-приложение на порту 3001 и подключается к базе данных по внутреннему имени хоста postgres. Сервис frontend-builder собирает React-приложение через Vite и копирует готовые статические файлы в volume frontend_dist. Сервис nginx использует образ nginx:1.28-alpine, слушает порты 80 и 443, выполняет редирект с HTTP на HTTPS, отдаёт frontend из volume и проксирует `/api/*` на backend.

Поток запроса в Docker-окружении выглядит следующим образом: браузер пользователя обращается к `https://localhost`, Nginx принимает TLS-соединение, отдаёт статические файлы SPA или направляет API-запрос во внутренний backend-контейнер, backend обращается к PostgreSQL по TCP внутри docker-сети. Такая архитектура делает Nginx единой публичной точкой входа, а backend и база данных остаются во внутренней сети Compose.

Для хранения пользовательских файлов предусмотрен volume backend_uploads. В нём размещаются аватары пользователей и изображения вопросов. Это позволяет сохранять файлы отдельно от слоя контейнера и не терять их при пересборке backend-образа.
